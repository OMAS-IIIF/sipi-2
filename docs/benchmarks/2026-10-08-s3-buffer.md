# Bounded S3 small-read buffer — 2026-10-08

## Implementation and source contract

The S3 source now retains at most 16 aligned 4 KiB pages for reads of at most
4 KiB (after clipping to the captured EOF). This is a per-open-source LRU, not a
cross-request/global cache: 64 KiB resident payload, plus one incoming page and
container/allocator overhead. Larger reads still bypass it and use the original
exact, conditional ranges capped at 1 MiB. Page allocation is lazy. No new CLI,
environment or TOML settings are introduced for these implementation bounds.

Small reads sharing one opened source serialize through its mutex, including
fills; different sources and direct large reads remain concurrent. Only completely
validated pages are admitted. Source copies share the same pinned cache. A detected
version change invalidates retained pages and makes later nonempty reads fail.
Transient/partial transfer failures do not populate a page; later explicit reads
may retry. No automatic SDK retry was added.

**Freshness:** every newly opened HTTP image/mask source still performs HEAD;
every actual GET retains If-Match/VersionId and response validation. A hit inside
an already opened source returns bytes of that captured snapshot, without remote
revalidation. Deletion/replacement during its lifetime is detected on a miss or
new opening. This is consistent with ByteSource's version-bound contract, but
is different from the old implementation's incidental GET on every read_at call.
The MinIO test now explicitly checks retained snapshot bytes, fresh-open failure,
and failure of previously warm pages after observing a change.

## Measured I/O, three repetitions

Same fixture/workload as the [S3 operation profile](2026-10-08-s3-io.md), with
128 uncached watermarked image requests, image metadata warmed beforehand, four
workers and eight clients. With mask retention enabled, image GET counts/bytes
below were identical in all three repetitions. Debug traces count actual SDK
calls, not logical reads or cache hits.

| Source | Image GETs per tile before → after | Payload per 128 tiles before → after |
| --- | ---: | ---: |
| master.tif | 19 → 6 | 12.67 → 14.68 MiB |
| master.jp2 | 10 → 10 | 317.33 → 317.33 MiB |

TIFF achieved the modeled **19 → 6 GETs/tile**, a 68% reduction in GET count with
15.9% more payload. JP2 GET count is unchanged; page alignment adds only 1,292 bytes
across all 128 requests. The cold mask still incurs four concurrent fills and then
uses its separate decoded-mask cache. Warm result hits still have **two HEADs and
zero GETs per image request**. All 4,608 measured profiling responses matched their
local references; temporary MinIO objects/bucket were removed.

## Paired throughput comparison (debug off)

The previously measured unbuffered Release executable was preserved before the
change. Baseline/current and result-cache on/off configurations were shuffled in
each of three repetitions. Both binaries used the same bucket/objects, enabled
mask cache, eight clients, four workers and one common local byte reference.
Without result caching, the warm phase rendered 512 images; with it, the phase
served 8,192 already encoded images. No build, sanitizer or second load test ran
concurrently. Normal desktop/Docker activity was not isolated.

Medians across trials; latency is the median trial p95. Cold result fill requests
128 distinct URLs and includes encoding/publication. Warm rendering still decodes
and renders each image; it has no encoded-result hits.

| Source | Scenario | Before req/s (range) | After req/s (range) | Before/after p95 ms |
| --- | --- | ---: | ---: | ---: |
| master.tif | Render, no result cache | 221.1 (206.7–232.7) | 509.8 (472.6–511.8) | 49.39 / 20.02 |
| master.tif | Cold result fill | 204.1 (181.1–215.1) | 406.5 (387.4–436.5) | 45.91 / 23.41 |
| master.tif | Warm result hits | 3288.1 (3206.0–3521.8) | 3299.2 (2749.0–3613.7) | 3.70 / 4.02 |
| master.jp2 | Render, no result cache | 64.0 (63.8–64.3) | 62.3 (62.0–62.6) | 157.17 / 161.69 |
| master.jp2 | Cold result fill | 58.6 (54.3–63.1) | 61.3 (59.9–61.8) | 167.64 / 167.57 |
| master.jp2 | Warm result hits | 3221.6 (3144.4–3770.6) | 3769.9 (3457.2–3809.1) | 3.86 / 3.06 |

TIFF rendering improved **2.31x**, from 221 to 510 images/s, with p95 falling from
49 to 20 ms. Cold result filling improved **1.99x**. This is a measured improvement
on these sources/local MinIO, not a cloud-capacity or universal TIFF guarantee.

JP2 rendering showed no gain: 64.0 → 62.3 images/s, about **2.7% lower**, with
p95 157 → 162 ms. The three trial ranges did not overlap for this scenario; the
cause is not isolated, so this is recorded as a small measured regression rather
than dismissed as proven noise. GET counts are unchanged and only 1,292 payload
bytes are added across 128 tiles. A focused follow-up should distinguish the new
per-source bookkeeping from SDK/decode/scheduling variation before any further
JP2 optimization. Cold result fill and warm cache-hit differences point in mixed
directions, so there is no basis for claiming a general JP2 improvement.

Warm result-hit throughput varies despite performing no GETs; the small-read
buffer cannot directly accelerate those hits. TIFF medians are nearly unchanged,
with a wide after range. Retain the counts and describe timing variability rather
than attributing every difference to buffering. Sampled SIPI RSS stays in the
same approximate range (26–47 MiB across warm scenarios); this is not a leak test
or a proof of an RSS ceiling.

## Validation and evidence

- Offline protocol fixture verifies exact GET ranges/counts for reuse, shared
  copies, page crossing, EOF, LRU eviction, concurrent same-page reads and direct
  large-read bypass without admission. It exercises failed/truncated fills and
  small/large conditional failures poisoning earlier cached pages.
- Real MinIO tests cover replacement, deletion, new openings, VersionId pinning,
  concurrent large reads, multi-range reads and TIFF/HTTP pixel equivalence.
- Full Debug/Release builds, ten focused Debug CTests (including fixtures), and
  four ASan/UBSan CTests (including fixtures) passed.
- I/O profiling checked 4,608 images; the paired throughput run checked 107,520.
  **All 112,128 measured responses matched**, with correct result-cache cardinality,
  clean child shutdown and deletion of the runner-owned MinIO buckets.

Raw evidence is in `build/s3-buffer-io-2026-10-08` and
`build/s3-buffer-throughput-2026-10-08`. The preserved baseline binary is
`build/s3-buffer-baseline-2026-10-08/sipi-2`. See
[reproduction commands](../benchmarks.md#paired-s3-small-read-buffer-comparison)
and [compact results](2026-10-08-s3-buffer.json). No deployment or result-cache
recipe change occurred; all rendered bytes are unchanged.
