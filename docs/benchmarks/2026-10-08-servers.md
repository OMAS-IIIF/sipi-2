# IIIF server comparison — 2026-10-08

This is a local aligned-TIFF-tile baseline, not a general product ranking. No server implementation or running OLDAP service was modified. See [method and reproduction](../server-comparison.md) and [machine-readable results](2026-10-08-servers.json).

Completed **96 timed trials**, **1,024,576 measured HTTP responses**, with no response-hash/status/MIME failures. Every trial used 128 regions in each output format, independently decoded before measurement; 24 server/cache processes × 256 reference outputs = 6,144 decoded references. Warmup requests are additional and not counted in the measured total.

## Eight concurrent clients

Numbers are median requests/second across three repetitions. Rendering has derivative/tile caches disabled, but warm metadata and OS caches. Cache-enabled results are fully warmed. Higher throughput is better.

| Server | Render JPEG | Render PNG | Cache on: JPEG | Cache on: PNG |
| --- | ---: | ---: | ---: | ---: |
| SIPI-2 0.1.0 | 1,106 | 353 | 8,817 | 3,936 |
| Cantaloupe 5.0.7 | 1,596 | 670 | 6,611 | 2,736 |
| IIPImage 1.3 | 2,479 | 1,141 | 4,702 | 1,306 |
| Triplet (pinned image) | 505 | 353 | 10,911 | 3,041 |

**These columns do not imply identical encoder or cache work.** Triplet JPEG uses its stock quality 75; others use 90, and SIPI-2 alone uses 4:4:4 chroma. IIPImage caches tiles in RAM, while the other three cache complete responses in a tmpfs filesystem. Triplet resamples the 1:2 TIFF requests from the main image; other servers return the corresponding precomputed pyramid pixels.

## What the measurements support

- IIPImage leads direct tile rendering in both formats in this matrix. It also generates slightly smaller PNGs than SIPI-2 with identical pixels. This is a useful future profiling target; it does not establish the cause of the difference.
- SIPI-2 leads cache-enabled PNG throughput. Triplet leads cache-enabled JPEG throughput, with much smaller and more lossy responses; this is not an equal-quality speed comparison.
- Cantaloupe beats SIPI-2 at eight-client direct rendering here. With one client, SIPI-2 renders JPEG faster. Avoid reducing this to “C++ versus Java.”
- SIPI-2 PNG is slower to generate than Cantaloupe PNG, but about 29% smaller for identical pixels. IIPImage shows that size alone does not explain the full performance difference.
- Trial variability is substantial in some cases (see complete ranges below). The first SIPI-2 JPEG render trials (one/eight clients) and first IIPImage parallel PNG render trial were notably slower. They are retained, not discarded. No cause was isolated; medians/ranges are descriptive, not statistical confidence claims.

## Output size and pixel checks

Mean bytes per response across all 128 tiles. JPEG MAE below uses only the 64 native-resolution tiles, comparing decoded RGB with original source pixels (0–255), so it excludes downsampling differences. This is a numerical distortion check, not a perceptual quality score.

| --- | ---: | ---: | ---: | --- |
| SIPI-2 0.1.0 | 21,440 | 87,497 | 3.079 | 4:4:4 |
| Cantaloupe 5.0.7 | 19,989 | 122,778 | 3.273 | 4:2:0 |
| IIPImage 1.3 | 20,094 | 84,620 | 3.303 | 4:2:0 |
| Triplet (pinned image) | 8,227 | 122,625 | 5.813 | 4:2:0 |

Native PNG pixels match exactly on every server. Both tested scales match the stored pyramid exactly for SIPI-2, Cantaloupe and IIPImage. Triplet’s 1:2 PNG differences are recorded in the JSON; the different resampling kernel is not a IIIF error. All reference bytes and pixel diagnostics were identical across repetitions and cache modes within each server.

Raw request timings, configurations, logs and runner snapshot are retained locally under `build/server-compare-2026-10-08/`. The checked-in summary retains every trial aggregate, per-server reference hashes/quality data and the raw report hash. The executed runner snapshot is hashed in the report; subsequent runner changes only add automatic summaries and explicit host-architecture/MIME guards, not different requests or timing.

The fixture is one synthetic 4096×4096 RGB8 LZW pyramid, not a corpus of real photographs/scans. No nonaligned crops, arbitrary scaling, rotation, TIFF compression alternatives, JPEG2000, S3, authorization, watermarks, cold storage, eviction, startup time or peak-memory benchmark is included. Cached file responses use tmpfs: no claim about durable-cache write performance. End-of-trial Docker stats are diagnostic only.
