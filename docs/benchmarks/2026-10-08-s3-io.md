# S3 operation profile — 2026-10-08

## Scope and correctness

The same Apple M5 Max / local Docker MinIO setup and Release build configuration
as the [watermark benchmark](2026-10-08-watermarks.md), now with opt-in S3 debug
traces. Eight clients, four workers, the same 4096x4096 TIFF/JP2 fixtures and
1024x512 coverage mask. Three shuffled repetitions per format/mode: mask cache
off/on while rendering 128 unique tile URLs without a result cache, and 512 warm
result hits with both caches on. Image metadata is warmed outside the measured
boundary; cold here means unrendered URLs and initially empty mask retention.

All **4,608 measured image responses** matched their one-worker local references.
Every measured response performed exactly one image HEAD and one mask HEAD. All
traced responses passed existing source-version/range validation. Warm result hits
performed no GETs. Temporary buckets were removed and child servers exited cleanly.
Setup, references, info requests and result-cache prefill are excluded from counts.

These diagnostic timings include SDK work, network/server time, response checks
and scheduling. Logging adds overhead. Concurrent durations overlap; their sums
are not wall time. Payload bytes are accepted buffer bytes, not HTTP/TLS wire
traffic. This is neither a CPU profile nor an AWS latency simulation.

## Image reads for 128 previously unrendered tiles

Mask cache enabled; image request counts/bytes were identical across all three
repetitions and with mask retention disabled. Times below are medians across
trials; operation p50/p95 values are medians of per-trial quantiles.

| Source | GETs/tile | GETs ≤1 KiB | Median GET size | Payload/tile | GET time/tile (sum) | GET p50/p95 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| master.tif | 19 | 2304/2432 (94.7%) | 6 B | 101.3 KiB | 14.26 ms | 0.669 / 1.179 ms |
| master.jp2 | 10 | 4/1280 (0.3%) | 65536 B | 2538.6 KiB | 20.45 ms | 1.105 / 6.888 ms |

TIFF sends **19 GETs per tile**, of which 18 are at most 1 KiB. The median size
is **6 bytes** (not the arithmetic mean). Common sizes are 2, 4, 6, 8, 168,
256 and 1024 bytes, alongside one larger image-data read per tile. It is therefore
worth targeting repeated small source reads instead of changing source freshness.

JP2 sends 10 GETs per tile on these fixtures. Most requests are 64 KiB or 1 MiB;
it transfers about 25 times as much image payload per output tile as this TIFF
pyramid. The codestream has 1024px tiles and its own packet/resolution layout;
this is not a claim that every JPEG2000 source behaves that way. Its larger reads
and decode work need different investigation from TIFF's tiny requests.

## Masks and warm results

Without mask retention there are 128 mask GETs per 128 image requests, each 3,319
bytes. With retention there are **four** initial mask GETs in every trial, then
none: the four workers can concurrently miss before any decoded mask is admitted.
This agrees with the documented independent cold-fill behavior; the count does
not justify adding synchronization complexity by itself.

For 512 warm result hits, each source format performs **512 image HEADs and 512
mask HEADs, with zero GETs**. The combined HEAD operation time averages about
0.92–0.96 ms per image request in this MinIO run. These sequential source checks
remain necessary under the current freshness contract. Overlapping worker timings
must not be treated as HTTP wall latency, and cloud round trips may be much larger.

## Read-buffer model, not an implemented optimization

We grouped ranges within each anonymous opened source (one pinned source snapshot),
never across image requests or object versions. Simply splitting every read into
4 KiB pages would be counterproductive: TIFF touches 3,891 such pages while making
only 2,432 actual GETs; JP2 touches 81,900 pages versus 1,280 GETs.

A more appropriate model buffers **only requests ≤4 KiB** in aligned 4 KiB pages,
while passing larger reads through unchanged. Count each distinct page once per
opened source, with no eviction, and clip the final page at object size:

| Source | Actual GETs | Modeled GETs | Actual payload | Modeled payload |
| --- | ---: | ---: | ---: | ---: |
| master.tif | 2,432 | 768 | 12.67 MiB | 14.68 MiB |
| master.jp2 | 1,280 | 1,280 | 317.33 MiB | 317.33 MiB |

For TIFF this is **19 → 6 GETs per tile**, a modeled 68% reduction in requests for
about 16% more payload. The small reads occupy five 4 KiB pages per opened TIFF
source in this workload. It is a promising bounded per-source buffer experiment,
not a measured speedup or a guarantee for other TIFFs. The same model barely
changes JP2's traffic. Actual buffering must respect range/EOF bounds, concurrent
reads, cache capacity, errors, and the already captured ETag/VersionId.

The next small implementation step should therefore be a bounded small-read buffer
for S3, preserving one current HEAD on source opening and all conditional GET checks.
Keep large reads direct, then rerun identical output/count/latency checks with debug
on for I/O evidence and debug off for throughput. No buffering was added in this step.
