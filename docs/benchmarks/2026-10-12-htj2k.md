# Lossless HTJ2K versus classic J2K and pyramidal TIFF — 2026-10-12

## Scope and correctness

Native Apple M5 Max / ARM64, 36 GiB RAM, macOS as recorded in the
[raw report](2026-10-12-htj2k.json), Apple Clang Release (`-O3 -DNDEBUG`).
Same production reader, resampler and JPEG writer for all formats. Grok 20.4.15,
one codec/benchmark worker; JPEG 90/4:4:4. CPU-only, warm local files, reused
metadata/handles. No HTTP, authorization, source opening, S3, result cache,
watermark, rotation or requested color conversion in timed work. No other
intentional builds/load tests ran during timing. Desktop/CPU/cache variation is
not eliminated. This is a render-core comparison, not a server throughput result
and not an x86 measurement.

Six existing reference TIFFs were read verbatim, without repeating normalization
or ICC conversion. Their hashes match the historical audited archive corpus;
all twelve existing JP2/pyramid input hashes also match the earlier comparison.
No original or existing derivative was changed. New JPH files are under
`build/htj2k-comparison-2026-10-12/`; only reports are tracked in Git.

The two JPEG 2000 variants use matching 1024×1024 tiles, 64×64 codeblocks,
six resolutions, one quality layer, LRCP progression, reversible 5/3 transform,
8-bit unsigned RGB, reversible RGB MCT and identical ICC bytes. The HT encoder
changes the block coding to HT-only and emits JPH branding and Part-15 markers;
these are inspected from actual bytes. This is a lossless comparison, not a
matched-perceptual-quality lossy experiment. Full-resolution validation decoded
all 280,961,064 pixels through the production reader in bounded windows and
compared every sample and ICC against the reference. Validation uses Grok, not
an independent HT codec; no general Part-15 conformance claim is made.

TIFF uses the unchanged 256×256 LZW/predictor pyramid with precomputed 2×2 mean
levels. TIFF's lower-resolution pixels are not required to match wavelet levels.
Classic JP2 and JPH, however, produce matching rendered pixel and JPEG fingerprints
for every measured request, including the same selected levels and decoded shapes.

Two runs, forward/reversed file order, each with two warmups and nine measured
iterations across 15 synthetic and 54 file cases. All 1,242 measured outputs are
stable across repetitions/runs; 972 include JPEG encoding. There are 324 matched
JP2/JPH timed request pairs. Preparation and validation precede both timed runs.
Raw samples, compiler version, fingerprints, source/binary/input hashes and coding
headers are preserved in JSON. Per-stage medians/sample counts and source hashes
were rechecked after completion.

## Render time

Arithmetic means over six images × nine samples × two runs per format/request.
Times include decode, resize and JPEG encoding/buffering, but exclude hashing.

| Request | TIFF ms | Classic JP2 ms | HTJ2K/JPH ms | JP2 → HT render speedup |
|---|---:|---:|---:|---:|
| thumbnail | 1.33 | 36.09 | 16.12 | 2.24× |
| preview | 34.37 | 437.32 | 67.89 | 6.44× |
| tile | 3.59 | 61.34 | 7.93 | 7.74× |

Decoding alone improves from 422.00 to 52.59 ms for previews (8.02×), and from
60.66 to 7.25 ms for tiles (8.37×). Resizing and JPEG encoding stay approximately
equal between the two wavelet formats. Thumbnail decode improves from 35.57 to
15.59 ms (2.28×), with a smaller gain on the map than on photographic images.
HT thumbnail core means differ between runs (15.40 and 16.84 ms), so report the
aggregate as approximate rather than a precise universal multiplier.

HTJ2K is faster than classic JP2 for every image/request in this corpus. Pyramidal
TIFF remains faster than HTJ2K for every image/request. These conclusions apply to
the specified prepared encodings, not all possible tiling/progression/compression
settings. Cached HTTP delivery bypasses the measured work.

## Reproduce

The existing prepared corpus is required. New output directories are mandatory.
The Python environment is the same Pillow environment used for archive preparation.

```sh
cmake --build build/release --target prepare-archive-image resize-benchmark -j 6
build/iiif-validator-venv/bin/python benchmarks/htj2k_compare.py \
  --output build/htj2k-comparison-repeat
```

The helper supports `--htj2k-reference REFERENCE_TIFF NEW_DIRECTORY` and a separate
`--verify-htj2k-reference REFERENCE_TIFF JPH` process, keeping encoder and production
reader runtime lifetimes separate. The runner leaves an incomplete report on
failure, compares coding headers and output fingerprints, and rehashes inputs.
The measured reference hashes were additionally checked against
`docs/benchmarks/2026-10-08-archive-corpus.json` during this run's audit.

Validation:

```sh
build/iiif-validator-venv/bin/python benchmarks/test_prepare_archives.py \
  build/release/prepare-archive-image
build/iiif-validator-venv/bin/python -m unittest discover -s benchmarks \
  -p test_htj2k_compare.py
```

All four preparation tests and both comparison-validation tests pass, including
RGB/gray roundtrip, unchanged ICC/source files, overwrite refusal, differing-pixel
rejection and unequal-coding/output rejection. Production code was not changed.

## Decision and next step

HTJ2K is a promising additional repository encoding when fast wavelet decoding
and smaller photographic masters than TIFF are useful. Keep pyramidal TIFF as
the established fast default; do not replace existing repositories automatically.
Next useful step: repeat this same current-code three-format experiment on the
Home x86 VM. The older resize Docker image's harness does not recognize `.jph`;
it must be updated before using it for this corpus. S3 I/O and lossy HTJ2K need
separate measurements. No Docker publication or deployment occurred here.
